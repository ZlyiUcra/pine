# Cap-combination survival sweep for ladder-cap

## Узгоджена пропозиція

Ladder Cap (CLI `checks/ladder-cap.js` і Electron GUI `ladder-cap-gui/`) вміє програти один
конкретний розклад ("схему") капів проти реального логу. Ця фіча додає статистику по всьому
простору можливих схем: скільки комбінацій капів, що в сумі дають рівно задану кількість кроків
драбини, вижили при прогоні проти завантаженого логу, скільки дійшли хоча б до одного блоуапу, і
скільки лишились незавершеними, коли лог скінчився - в кількості і у відсотках від загальної
кількості перевірених комбінацій. Реалізується і в CLI, і в GUI, з однією спільною логікою
класифікації в `checks/ladder-cap-core.mjs`, яку обидва боки імпортують.

При розслідуванні виявилось, що GUI вже рахує майже весь потрібний матеріал (перебір комбінацій,
прогін кожної проти логу, підрахунок блоупів) для власних таблиць підказок - ця фіча додає
підсумковий рядок статистики над тим, що вже обчислено, а не новий важкий прохід.

## Межі та обмеження

- В скоупі: одна спільна функція класифікації (SURVIVED / BLEW UP / STILL OPEN AT LOG END) в
  `ladder-cap-core.mjs`, використовувана і CLI, і GUI.
- В скоупі: новий CLI-прапорець для набору капів комбінаторики (не `--caps`, який уже означає
  ANOTHER Thing в обох поверхнях).
- В скоупі: валідація `steps` (ціле число, верхня межа) в обох поверхнях - без цього кількість
  комбінацій (2^(steps-1)) необмежено росте від поля, яке користувач редагує напряму.
- В скоупі: дрібне торкання GUI - `blocksForCap` переноситься в core (зараз задубльований), нова
  секція статистики на сторінці.
- Поза скоупом: об'єднання існуючого `--caps`-свіпу (незалежні фіксовані капи) з новою
  комбінаторикою в один код-шлях - лишаються окремими, щоб не чіпати вже робочу поведінку.
- Поза скоупом: підняття дубльованих TypeScript-типів (`LogRow`, `LadderDetail` та інші) з
  `.d.mts` у `main.ts` - реальний дубль, але CLI не типізований і нічого від нього не отримує;
  відкладено без гейту.
- Поза скоупом: risk-aware метрика (глибина near-miss, drawdown) - обраний метод структурно
  ризик-сліпий (carry ніколи не рухає баланс), відомий і прийнятий ліміт v1, не виправляється
  зараз.

## Зауваження, що вціліли

- [підтверджено, 5/5 незалежно] Пропозиція спершу описувала GUI як порожній каркас - хибно.
  `ladder-cap-gui/src/renderer/src/main.ts` вже імпортує `capCombinations`/`capCombinationsUpTo`,
  вже прогонює кожну комбінацію через `simulateLadder` і вже рахує блоупи для власних таблиць
  підказок. Реальний обсяг роботи - значно менший за первинний опис.
- [підтверджено] `blocksForCap` існує в `ladder-cap-core.mjs`, не експортований; GUI носить
  побайтову копію в `main.ts`. Експортувати з core, GUI імпортує.
- [підтверджено] `checks/ladder-cap-core.d.mts:46` стверджує, що `schedule` "cycled" - неправда з
  2026-08-08 (грається один раз, не заходить по колу). Реальний ризик для коду, що писатиметься
  проти цього контракту, не косметика.
- [підтверджено] `steps` не валідується як ціле і без верхньої межі в обох поверхнях. Кількість
  комбінацій - рівно 2^(steps-1); steps=14 вже ~9с заморозки GUI-рендерера (виміряно), steps=20 -
  OOM. Нецілий steps дає `NaN%`.
- [підтверджено] `--caps` уже має два несумісні значення (CLI: N незалежних прогонів; GUI:
  ОДИН розклад) - третє значення (набір для комбінаторики) вимагає окремого прапорця.
- [підтверджено, виміряно] Наївний бінарний критерій "вижив = blowups===0" не узгоджений з тим,
  що GUI вже вимагає для власних підказок (`isAcceptable`: немає блоупу І прибуток > 0). І 76%
  "вижилих" на реальному лозі (`log-0708-m1.csv`) виявились просто незавершеними послідовностями
  (`openAtEnd != null`), коли лог скінчився - не доведено безпечними.
- [підтверджено, виміряно] Відсоток "вижилих" залежить від того, яку множину капів рахують
  (capCombinations vs capCombinationsUpTo дають різні знаменники - 256 проти 511 на steps=9,
  86.3% проти 73.6% на реальному лозі) і від глибини драбини (steps=8 -> 61%, steps=13 -> 97%,
  бо глибша драбина заповнюється схемами, які структурно не можуть вичерпатись). Кожне число
  друкується разом зі своєю популяцією.
- [підтверджено] Похідні статистики (survived/blew up) рахуються фільтрацією вже обчислених
  результатів, не другим повним прогоном - GUI вже прогонює весь пул для власних таблиць.
- [підтверджено] CLI не повинен друкувати комбінаторику через існуючий `--detail`-шлях - 256
  комбінацій x сотні вікон дало б ~94000 рядків. Тільки агреговані числа.

## Позначене допитувачем

- [слабке] security F2 ("% росте, коли доказів менше") - розщеплено на допиті: обрізаний лог
  (менше вікон -> 100%) - загальна статистична пастка будь-якої бінарної метрики на розріджених
  даних, не специфічний дефект пропозиції; лікується показом лічильників поруч з відсотком.
  Глибина драбини (steps росте -> % росте) - НЕ та сама пастка, лишається специфічним дефектом
  визначення популяції, лічильниками не лікується - рішення користувача: явний підпис
  steps/rung-limit біля кожного відсотка.
- [слабке] security F7 (`dedupeRows` поза core) - виміряно, що на реальних даних не змінює жодного
  числа (`oneAtATime` вже відкидає точний дублікат). Лишається структурним зауваженням, не
  блокером.
- [первинно BLOCKS, знято на допиті] nitpicker і best-practices спочатку заблокували на
  первинному формулюванні пропозиції ("будувати в GUI з нуля" - хибна передумова). Обидва зняли
  BLOCKS за умови виправленого скоупу: CLI-фіча плюс видалення дублікатів у GUI
  (`blocksForCap`, спільний критерій SURVIVED, фікс `.d.mts`), без підняття типів (best-practices
  сама назвала це необов'язковим, pragmatist прямо відмовився від нього як від умови).

## Рішення користувача (по відкритих питаннях ради)

- **Популяція комбінацій:** точна сума (`capCombinations`), не `capCombinationsUpTo`. CLI і GUI
  матимуть різні знаменники за замовчуванням (CLI набір капів вводиться, GUI - повний діапазон
  1..steps) - кожне число друкується з підписом своєї популяції.
- **Незавершені на кінець логу (`openAtEnd`):** окрема третя категорія (SURVIVED / BLEW UP /
  STILL OPEN AT LOG END), не змішується з "вижив" і не відкидається мовчки.
- **Критерій SURVIVED:** узгоджено з GUI - немає блоупу І період закрився в прибутку (те саме,
  що `isAcceptable` вже вимагає для підказок).
- **Маршрут:** direct-verified, з дрібним торканням GUI (без нового екрану чи IPC-каналу).

## Свідомо не робимо

- Об'єднання `--caps`-свіпу з новою комбінаторикою в один код-шлях (найменший диф, наявна
  поведінка не чіпається).
- Підняття дубльованих типів з `.d.mts` у `main.ts` (реальний дубль, але не блокує цю фічу;
  CLI не типізований).
- Risk-aware метрика (near-miss глибина, drawdown) - відомий ліміт v1 моделі, не в цій фічі.
- Worker/Cancel/progress bar для свіпу - виміряно ненеобхідним при обмеженому steps (~40мс на
  256 комбінацій).
